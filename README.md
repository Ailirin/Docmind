# DocMind

[![CI](https://github.com/Ailirin/Docmind/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/Ailirin/Docmind/actions/workflows/ci.yml)
[![codecov](https://codecov.io/gh/Ailirin/Docmind/branch/main/graph/badge.svg)](https://codecov.io/gh/Ailirin/Docmind)
![Python](https://img.shields.io/badge/python-3.12%20%7C%203.13-blue)

Сервис обработки медицинских PDF: принимает выписки, рецепты и диагнозы, извлекает структурированные данные и возвращает их через REST API.

Где какой файл лежит: [`FILES.md`](FILES.md).

---

## Задача

В клиниках и страховых компаниях много сканов и PDF: выписки, рецепты, заключения.  
Людям приходится **вручную** читать файлы и переносить в систему ФИО, диагноз, препараты, даты.

Это медленно, дорого и легко ошибиться. При росте объёма документов ручная обработка не масштабируется.

Нужен сервис, который:

1. принимает документ;
2. сам извлекает из него важные поля;
3. показывает статус и результат;
4. не «висит» у пользователя, пока идёт тяжёлая обработка.

---

## Решение

**DocMind** — конвейер обработки документов:

| Шаг | Что происходит |
|-----|----------------|
| 1. Приём | Клиент загружает PDF. Система сразу отвечает: «принято, вот номер заявки». |
| 2. Очередь | Тяжёлая работа уходит в отдельный фоновый процесс — API не тормозит. |
| 3. Разбор | Из PDF достаётся текст, определяется тип документа (выписка / рецепт / диагноз). |
| 4. Сущности | Из текста собираются поля: пациент, диагноз (код МКБ), лечение, дата. |
| 5. Результат | Данные сохраняются; по номеру заявки — статус и готовый результат. |
| 6. Контроль | Веб-админка со списком документов (с пагинацией). |
| 7. Наблюдение | Видно, сколько документов обработано, где ошибки, что пишут логи. |

Разбор полей — два режима:

- **mock (стабильный)** — по regex-правилам, без LLM (для тестов и демо);
- **llm** — через OpenAI-совместимый API (Ollama и другие), с retry при сетевых сбоях и **автоматическим fallback на regex-экстрактор** при недоступности LLM: документ получает статус `done` вместо `failed`, результат помечается `extractor=regex_fallback`.

## Результат

| Было | Стало |
|------|--------|
| Человек читает PDF и копирует поля | Система заполняет карточку документа сама |
| Долгое ожидание ответа при разборе | Сразу «принято»; результат догоняет по статусу |
| Непонятно, где застрял документ | Статусы: `queued → processing → done / failed` |
| Сложно показать работу сервиса | Админка + дашборды мониторинга |
| Страшно отдавать наружу API | Ключ доступа, лимиты на файл, закрытые метрики |

На выходе по каждому документу:

- кто пациент;
- какой диагноз (код МКБ и название);
- какое лечение (препарат и дозировка);
- дата документа;
- исходный извлечённый текст (для проверки человеком).

## Качество извлечения (eval)

Gold-набор: **200 кейсов, 530 проверяемых полей** (`patient.full_name`, `diagnosis.code`, `treatment.medication`) + классификация типа документа. Запуск: `python scripts/run_eval.py --provider mock|llm`, подробности — [`eval/README.md`](eval/README.md).

| Экстрактор | Классификация типа | Поля (micro) | patient | diagnosis.code | medication |
|------------|-------------------:|-------------:|--------:|---------------:|-----------:|
| mock (regex) | 200/200 = 100% | 530/530 = 100% | 185/185 | 185/185 | 160/160 |
| LLM, промпт v2 | 200/200 = 100% | 114/530 = 21.5% | 95/185 | 14/185 | 5/160 |
| LLM, промпт v3 (текущий) | 200/200 = 100% | 529/530 = **99.8%** | 185/185 | 185/185 | 159/160 |

Переход промпта v2 → v3 поднял точность полей с 21.5% до 99.8% на одном и том же наборе — это результат итераций над промптом и нормализацией ответа (`_normalize_diagnosis_fields`, `_fill_from_text`).

> **Важно:** кейсы синтетические — сгенерированы по шаблонам (`Patient: … Diagnosis: …`, `scripts/generate_eval_cases.py`), а не взяты из реальных документов. Поэтому 100% у regex-экстрактора ожидаемы: это регрессионный тест, а не оценка точности на реальных выписках. Оценка на реальных (обезличенных) документах — следующий шаг.

## API

| Метод | Путь | Описание |
|-------|------|----------|
| `POST` | `/api/v1/documents` | Загрузить PDF → `202 Accepted` + `document_id` |
| `GET` | `/api/v1/documents` | Список документов (пагинация, фильтр по статусу) |
| `GET` | `/api/v1/documents/{id}` | Карточка документа и результат извлечения |
| `POST` | `/api/v1/documents/{id}/process` | Ручной запуск обработки |
| `GET` | `/api/v1/health` | Liveness |
| `GET` | `/api/v1/health/ready` | Readiness (DB + RabbitMQ) |
| `GET` | `/metrics` | Prometheus-метрики (Basic Auth) |

Все эндпоинты кроме health требуют заголовок `X-API-Key`.

**Пагинация и фильтрация списка:**

```
GET /api/v1/documents?limit=20&offset=0&status=done
```

Ответ:
```json
{
  "items": [...],
  "total": 142,
  "limit": 20,
  "offset": 0,
  "has_next": true
}
```

## Быстрый старт

Нужны Docker Desktop и несколько минут.

```powershell
cd D:\Project\DocMind
Copy-Item .env.example .env
docker compose up -d --build
```

| Что открыть | Адрес | Зачем |
|-------------|--------|--------|
| Описание API | http://127.0.0.1:8000/docs | Swagger UI — загрузить PDF через интерфейс |
| Админка | http://127.0.0.1:8000/admin/documents | Список и карточки документов |
| Мониторинг | http://127.0.0.1:3000 | Grafana — графики и логи |

Все пароли и ключи (`API_KEY`, `ADMIN_PASSWORD`, `METRICS_PASSWORD`, `GRAFANA_ADMIN_PASSWORD`, `POSTGRES_PASSWORD`, `RABBITMQ_PASSWORD`) берутся из `.env`; обязательные переменные без значения останавливают `docker compose up` с понятной ошибкой. В `.env.example` стоят демо-значения (`change-me`) — **перед любым деплоем замените их** и не коммитьте свой `.env`.

Порты опубликованы только на `127.0.0.1`. Promtail (сбор логов, монтирует `docker.sock`) вынесен в `docker-compose.override.yml` — он подхватывается автоматически в dev. Для prod: `docker compose -f docker-compose.yml up -d`. Версии образов закреплены (без `:latest`).

После правок кода — пересборка образа:

```powershell
docker compose up -d --build --force-recreate api
```

Тестовые PDF лежат в `samples/`.

### Переключение режима LLM

По умолчанию — mock-режим: быстро и без модели. Переключение **без правки** `docker-compose.yml`.

**Через `.env`** (Compose подхватит сам):

```env
EXTRACTOR_PROVIDER=llm
```

```powershell
docker compose up -d ollama
docker exec -it docmind-ollama ollama pull llama3.2:1b
docker compose up -d --force-recreate api worker
```

Вернуть mock: в `.env` снова `EXTRACTOR_PROVIDER=mock` и та же команда `--force-recreate`.

**Только на этот запуск** (PowerShell):

```powershell
$env:EXTRACTOR_PROVIDER = "llm"
docker compose up -d --force-recreate api worker
```

### Настройка логирования

По умолчанию — plaintext (удобно локально). Для Loki/ELK включите JSON:

```env
LOG_FORMAT=json
LOG_LEVEL=INFO
```

Каждая строка лога становится валидным JSON-объектом с полями `timestamp`, `level`, `logger`, `request_id`, `message`.

## Тесты

```powershell
# Unit-тесты (быстро, без Docker)
venv\Scripts\python -m pytest

# Интеграционные тесты (требуют Docker)
venv\Scripts\python -m pytest -m integration

# Все вместе
venv\Scripts\python -m pytest -m "integration or not integration"
```

| Тип | Количество | Что проверяет |
|-----|-----------|---------------|
| Unit | 121 | API, worker (handle_message, backoff, SIGTERM), LLM-экстрактор (retry, парсинг), fallback-экстрактор, исключения, admin, classifier, processor, publisher, schemas, безопасность (fail-closed секреты, ReDoS) |
| Integration: file_storage | 14 | Реальная ФС: атомарность, round-trip, крупные файлы |
| Integration: DB | 20 | Реальный PostgreSQL: CRUD, JSONB, фильтры, пагинация, стабильный порядок, count |
| Integration: API | 14 | HTTP (`httpx.AsyncClient`) + реальная БД: upload, GET, пагинация и фильтры, валидации, API-ключ |
| Integration: processor | 9 | Полный pipeline: sample PDF → DB, все статусы, идемпотентность |

Интеграционные тесты используют `testcontainers` (PostgreSQL в Docker) и изоляцию через `SAVEPOINT` — без truncate таблиц между тестами. Миграции Alembic накатываются в контейнер один раз на сессию; приложение в тестах работает в одном event loop с тестом (`httpx.AsyncClient` + `ASGITransport`), см. [`FILES.md`](FILES.md#интеграционные-тесты-testsintegration). Всего: 121 unit + 57 integration = 178.

## Что заложено «как во взрослом сервисе»

- **Очередь задач** — пики загрузок не роняют API.
- **Отдельный worker** — разбор масштабируется независимо; DLQ для «ядовитых» сообщений.
- **Graceful shutdown** — worker дообрабатывает текущее сообщение перед остановкой по SIGTERM.
- **Retry с backoff** — LLM-запросы повторяются до 3 раз при сетевых сбоях.
- **Fallback-экстрактор** — при недоступности LLM автоматически переключается на regex (`FallbackEntityExtractor`); `docmind_extractor_fallback_total` в Prometheus для алертинга.
- **Атомарная запись файлов** — tempfile + `os.replace`; файл либо полный, либо его нет.
- **Настраиваемый пул соединений** — `db_pool_size`, `max_overflow`, `pool_recycle` в конфиге.
- **Структурированные логи** — `request_id` в каждой строке; JSON-режим для Loki.
- **Предупреждение о небезопасных дефолтах** — конфиг ругается при запуске с `api_key=change-me`.
- **Миграции БД** — схема версионируется через Alembic.
- **Единый идентификатор запроса** — `X-Request-ID` сквозь API → очередь → worker.
- **Метрики** — upload/process счётчики, histogram latency, fallback-счётчик; закрыты Basic Auth.
- **CI/CD** — GitHub Actions: lint (Ruff) → unit-тесты (Python 3.12 + 3.13) → integration-тесты на каждом PR; автоотмена устаревших прогонов.
